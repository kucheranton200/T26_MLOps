## 1. Цель и границы работы

Упаковать проверенную систему варианта 10 в воспроизводимый OCI-образ, запустить её через Docker Compose с ограниченными правами и подтвердить готовность и предсказание реальными HTTP-запросами. Различать build-time и runtime, image и container, health и readiness, воспроизводимый tag и `latest`.

### Командный результат (по методичке, раздел 3)

1. Многостадийный `Dockerfile`: стадия `quality` (Ruff, pytest, валидация контракта, обучение модели) и стадия `runtime`, которая зависит от успешной `quality`.
2. `.dockerignore` с минимальным build context.
3. `compose.yaml` без поля `version`.
4. Процесс в контейнере работает от non-root пользователя с явным UID/GID.
5. Healthcheck по `/readyz`.
6. В Compose: `read_only: true`, `tmpfs: /tmp`, `cap_drop: ALL`, `no-new-privileges`.
7. Образ `mlops-students-dropout:lr6-<short-sha>` (имя образа см. раздел 10).
8. `reports/container/lr6-inspect.txt`: image ID, размер, пользователь, healthcheck.
9. `reports/container/lr6-smoke.json`: ответ `/predict`.
10. Таблица «риск — ограничение — проверка».
11. Issue, pull requests, review, индивидуальные evidence cards, tag `lr6-v1`.

`latest` не принимается как идентификатор результата. Секреты, токены и персональные данные не попадают в Dockerfile, build arguments, labels, слои образа и отчёты.

### Что не входит в ЛР6

- расширение API-контракта и проверки через OpenAPI (ЛР7): в ЛР6 только минимальный сервис;
- разделение CI на `quality` и `container` (ЛР8);
- реестр моделей и управляемый выпуск (ЛР10);
- метрики и дашборды (позже по курсу), `/metrics`;
- публикация в реестр образов и registry digest (итоговый release).

Контейнерная граница ЛР6 остаётся неизменной в ЛР7: `/healthz`, `/readyz`, `/predict`, порт 8080 и модельный bundle. Названия и порт поэтому берём ровно как в методичке.

## 4. Договорённости по интерфейсу для параллельной работы

Пути указаны от корня репозитория. Договорённости фиксируем до начала работы, чтобы сервис, тесты, образ и Compose писались параллельно.

### 4.1 Минимальный HTTP-сервис

Порт внутри контейнера 8080. Имена эндпоинтов и порт фиксированы методичкой и сохраняются в ЛР7.

| Метод | Путь | Вход | Ответ | Коды |
|---|---|---|---|---|
| GET | `/healthz` | - | `{"status": "ok"}`: процесс отвечает | 200 |
| GET | `/readyz` | - | `status`, `model_version`: модель загружена, признаки совпадают | 200; иначе 503 с `reason` |
| POST | `/predict` | JSON: 6 признаков ранней конфигурации (Age, Gender, DaytimeAttendance, Scholarship, PrevGrade, AdmissionGrade) | `predicted_class`, `probabilities` (Dropout, Enrolled, Graduate), `model_version`, `request_id` | 200, 422 |

Правила:

- модель грузится один раз при старте; при отсутствии или порче файла сервис **не падает**, а отвечает 503 на `/readyz` (этого требует негативный сценарий методички); `/predict` при неготовой модели тоже отвечает 503;
- загрузка только через skops, список недоверенных типов должен быть пустым (ADR 0002); иначе сервис не готов;
- `model.feature_names_in_` должен совпасть со схемой запроса; иначе сервис не готов;
- диапазоны входных значений берутся из `data/students_contract.json`, не дублируются вручную; лишние поля и пропуски дают 422;
- `request_id` уникален для каждого запроса; `model_version` формирует @Vikabh (предложение: конфигурация признаков и первые 12 символов SHA-256 файла модели), выбор описывается в PR и ADR;
- в ответах нет секретов и персональных данных.

### 4.2 Образ и Compose

| Элемент | Требование |
|---|---|
| Базовый образ | явная версия Python 3.12 slim, обе стадии |
| Стадия `quality` | зависимости `.[dev,data,tracking]`; затем по порядку: Ruff, валидация контракта студентов, `preprocess`, `split_data`, `train` (параметры из `students/params.yaml`, конфигурация `early`), pytest. Любой отказ останавливает сборку. DVC в образ не ставится: этапы запускаются модулями напрямую |
| Стадия `runtime` | зависимости только `.[serve]`; код приложения и `model.skops` копируются из `quality` выборочно; нет tests, data, инструментов разработки, MLflow-хранилища, отчётов |
| Пользователь | non-root с явным числовым UID/GID (например, 10001:10001) |
| Запуск | exec-форма `CMD` (uvicorn на 8080), `EXPOSE 8080` |
| Healthcheck | `/readyz` через Python (`urllib`), без `curl`; код выхода ненулевой при 503 |
| Переменные | `MODEL_PATH` (по умолчанию `/app/models/model.skops`); секретов нет |
| Python в runtime | `PYTHONDONTWRITEBYTECODE=1`, чтобы работать при `read_only` |
| Tag | `mlops-students-dropout:lr6-<short-sha>`; `latest` не используется |
| Compose: сервис | `app`, `build: .`, `image` с обязательной переменной `IMAGE_TAG` (без значения по умолчанию, чтобы не собрать `latest`) |
| Compose: порт | `${APP_PORT:-8080}:8080`; при занятом порту меняется `APP_PORT`, а не порт контейнера |
| Compose: ограничения | `read_only: true`, `tmpfs: /tmp`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]` |
| Compose: прочее | свой `healthcheck`, без верхнеуровневого `version` |

Порядок слоёв: зависимости до часто меняющегося кода, где это возможно.

### 4.3 Команды (PowerShell, из корня)

```powershell
git switch -c lab6/<логин>-work
docker version
docker compose version
python -m pytest -q

$env:IMAGE_TAG = "lr6-$(git rev-parse --short HEAD)"
docker build --pull --tag "mlops-students-dropout:$($env:IMAGE_TAG)" .

docker compose up --build --detach
docker compose ps
docker compose logs --no-color app
docker inspect --format '{{json .State.Health}}' <container-id>

python scripts/container_smoke.py --base-url http://127.0.0.1:8080 --output reports/container/lr6-smoke.json

docker image inspect "mlops-students-dropout:$($env:IMAGE_TAG)" --format 'id={{.Id}} size={{.Size}} user={{.Config.User}} health={{json .Config.Healthcheck}}'
docker run --rm --entrypoint python "mlops-students-dropout:$($env:IMAGE_TAG)" -c "from pathlib import Path; print([p.name for p in Path('/app').iterdir()])"

docker compose down
```

Не заменять ожидание готовности длинным `sleep`: опрашивать `/readyz` или `docker inspect` до timeout. Результат `docker image inspect` вместе с командой сохраняется в `reports/container/lr6-inspect.txt`; файл должен быть с LF и без BOM (в Windows PowerShell 5.1 `Out-File -Encoding utf8` добавляет BOM, поэтому использовать PowerShell 7 или записывать из Python).

### 4.4 Порядок финальной сборки

Методичка требует связать образ с commit. Чтобы отчёты не меняли commit сборки:

1. До заморозки (Ср 25.11, 20:00) в `main` вливаются все PR с кодом и `README.md`.
2. После заморозки в `main` попадают только `docs/` и `reports/`. Оба каталога исключены `.dockerignore`, поэтому build context и образ не меняются.
3. Образ собирается из `main` после заморозки; SHA этого commit попадает в tag образа, inspect-отчёт и записку.

Порядок сдачи как в ЛР5; если требования для ЛР6 изменятся, это записывается в «Отклонения».

1. Каждый ведёт одну ветку `lab6/<логин>-work` от актуального `main`.
2. PR открывается в `kucheranton200/T26_MLOps` по ссылке `https://github.com/kucheranton200/T26_MLOps/compare/main...lab6/<логин>-work`; слева должен быть репозиторий команды, а не преподавателя.
3. Merge после зелёного CI (Ruff, pytest, `dvc repro`) и одобрения другого участника.
4. В ДО.СКИФ сдаётся ссылка на свой влитый PR; @kucheranton200 сдаёт ссылку на `main`.
5. Тег `lr6-v1` ставится после слияния всех PR и не переставляется.

Evidence card каждого участника содержит поля методички (раздел 17): ФИО, группа, команда, логин; ЛР6, commit/tag и image ID; роль в ЛР6 и отличие от ЛР5; задача (issue с наблюдаемым критерием); личный артефакт; вклад; инженерное решение с отвергнутой альтернативой; риск, который выявляет healthcheck, inspect или smoke test; диагностика (команда, первый полезный фрагмент лога, причина); **использование ИИ** (инструмент и самостоятельно проверенные утверждения либо отсутствие использования).

Минимальный допуск: версия команды зафиксирована, образ связан с commit, личная issue закрыта через PR, review выполнено другим участником, контейнер `healthy`, личная проверка воспроизводится.

Защита (3–4 минуты): tag, ID образа и commit; объяснение одной стадии или ограничения; запуск собственной проверки; назначенный отказ, поиск причины в логе или inspect, исправление; ответ, почему образ нельзя идентифицировать словом `latest`. Преподаватель может изменить `APP_PORT`, убрать модель из build stage, назначить проверку пользователя или попросить показать файл, исключённый из context. Репетиция этих сценариев входит в задачу 15.

## 9. Решения команды

Предложены координатором, считаются принятыми после одобрения плана в PR.

1. **Контракт методички сохраняем дословно.** `/healthz`, `/readyz`, `/predict`, порт 8080, tag `lr6-<short-sha>`: этот контракт продолжается в ЛР7.
2. **Модель строится внутри build.** Так делает методичка для воспроизводимости; перенос готового файла отвергнут и записывается в ADR.
3. **Формат skops, не joblib.** В методичке пример с `models/model.joblib`, но `joblib` основан на pickle, а ADR 0002 запрещает pickle. Отклонение фиксируется в ADR и отчёте; позиция преподавателя уточняется (раздел 10).
4. **Тесты ЛР4 и ЛР5 становятся gate сборки.** Если какие-то из них читают артефакты `students/models/`, которых нет в context, порядок стадии `quality` (обучение до pytest) или правка теста решается отдельной issue, но тесты не отключаются и не получают `skip`.
5. **Не готовая модель не роняет сервис.** Недоступная модель даёт 503 на `/readyz`, а не завершение процесса: так проверяется негативный сценарий методички.
6. **Минимальный runtime.** Выборочный `COPY`, `.dockerignore` и проверка листинга `/app`; лишнее не копируется изначально, потому что удалённый позже слой остаётся в истории образа.
7. **Безопасность по умолчанию.** non-root с числовым UID/GID, `read_only`, `tmpfs`, `cap_drop: ALL`, `no-new-privileges`; секретов нет ни в build arguments, ни в labels, ни в отчётах.
8. **Отчёты создаются командами.** Ручная правка `lr6-inspect.txt` и `lr6-smoke.json` является стоп-фактором.
9. **Артефакты коллег.** Каждый пишет свои файлы и свою evidence card.

## 12. Зависимости и риски

- **Связь с ЛР5.** Слияние плана ЛР6 разрешено только после тега `lr5-v1`. Фикстуры ЛР5 переиспользуются в тестах API.
- **Docker на машинах участников.** Docker Desktop на Windows требует WSL2 или виртуализацию; проверка в задаче 0; запасной путь: общий runner преподавателя.
- **Версии библиотек.** skops и scikit-learn чувствительны к версиям: версия, которой обучена модель в `quality`, и версия в `runtime` должны совпасть; расхождение записывается в заметки о сборке.
- **Read-only и запись.** Приложение не должно писать вне `/tmp`; кэш байткода отключён; проверяется в задаче 8 и defect injection @GlooshSl.
- **CRLF.** `Dockerfile`, `compose.yaml` и скрипты с CRLF ломают сборку и запуск. `.gitattributes` и проверка `git ls-files --eol` обязательны; отчёты `reports/container/` тоже должны быть с LF.
- **Время сборки.** Обучение внутри `quality` увеличивает build; допустимо, пока набор данных синтетический (1200 строк); время фиксируется в заметках.
- **Конфликты README.** Раздел о контейнере правит один PR (@Z0rko32); остальные README не трогают или обновляются от `main`.
- **Нет ответа участника до срока.** Задача переходит @GlooshSl или @kucheranton200 по договорённости, запись в «Отклонения».
